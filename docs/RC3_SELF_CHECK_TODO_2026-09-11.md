## 结论与检查范围

建议先修口型，再做稳定性和提醒正确性，最后补日常使用功能。最重要的新发现是：**嘴部 Part 只有一层开启，并不保证真正绘制出来的嘴可见。rc3 的担心态和部分说话幅度仍会无嘴。**

本轮完成：

- 17 个自有 JavaScript/MJS 文件语法检查通过。
- 68 条台词 ID 无重复，68 个 WAV 全部存在，均为 PCM、32 kHz、单声道、16 bit；13 项模型资源引用完整。
- 桌面 rc3 的 `app.asar` 为 `1.4.0-rc.3`，119 个自有文件与当前源码逐字节一致；Pixi/Live2D 的浏览器脚本目录仍在，没有混入根目录的旧构建目录。未逐文件比对所有第三方依赖。
- 使用实际 `vendor/live2dcubismcore.min.js` 和实际 `.moc3`，在内存中检查最终嘴部 Drawable 透明度。
- 对菜单、语音队列、天气切城、断网、安静时间等运行真实函数的隔离模拟；文件系统写入、网络与时钟按需替换为内存实现。

未完成的验收：本轮没有进行 Windows 界面操作、6–12 小时连续运行、双显示器热插拔、不同显卡性能测试或 68 条语音逐条试听。因此，模拟确认的逻辑缺陷与需要实机量测的体验优化分开列出，不能将文件完整性等同于听感或画面完全正常。

## 已确认的问题／明确的保护缺口

优先级：P1＝建议下一轮先做；P2＝影响正确性或常见体验，随后处理；P3＝细节。规模是相对改动范围，不是工时承诺。

### B01 · P1 · 修复最终可见口型，而不只检查 Part 互斥〔中〕

- [ ] 校准担心态的表情参数与担忧嘴形，修正说话档位映射，并增加最终绘制可见性检查。
- 证据：`app/renderer/renderer.js:66`、`:252`、`:259`、`:261`。实际 Core + moc3 内存复测如下：

| 输入情形 | 选中 Part 的透明度 | 最终嘴部图像 |
|---|---:|---|
| 担心、未说话 | 1 | 所有嘴部 Drawable 均为 0 |
| 不高兴、未说话（对照） | 1 | 担忧嘴正常可见，透明度 1 |
| 默认表情说话、幅度 0 | 1 | 所有嘴部 Drawable 均为 0 |
| 默认表情说话、幅度 0.30 | 1 | 所有嘴部 Drawable 均为 0 |
| 默认表情说话、幅度 0.62 | 1 | 最大嘴仅约 0.05 透明度 |
| 惊讶、未说话（对照） | 1 | 中等嘴正常可见，透明度 1 |

- 原因：模型内部还会根据 `ParamMouthForm` 和 `ParamMouthOpenY` 控制嘴图像透明度。当前逻辑会提前选中尚未显现的下一档嘴，并关闭上一档；担心态的嘴形参数也与所选图层不匹配。现有自检只看 Part，因此漏报。
- 验收：所有常驻表情和说话幅度扫描均有正确的可见嘴；仍保持嘴层互斥；**非说话状态绝不使用最大档嘴型**。补正常速度和慢放录像确认过渡。

### B02 · P1 · 防止一次播放异常后永久不再说话〔中〕

- [ ] 增加播放启动确认超时、播放完成超时与异常释放；渲染进程故障时清理音频／字幕状态并有限次恢复。
- 证据：`app/trigger-engine.js:208`、`:407`、`:469`；`app/main.js:674`、`:677`。
- 已模拟：首条语音派发后收不到完成回调，推进 10 分钟，`speechActive` 仍为 true；第二条手动点播只能排队。
- 明确缺口：渲染退出当前只记录控制台日志，没有恢复入口。此项模拟的是异常回调丢失，不表示正常播放必然卡死。
- 验收：模拟启动失败、播放悬置、渲染退出后，可继续点播；旧回调不能结束新语音；不会出现无限重启或多条音频叠播。

### B03 · P1 · 单实例与“找回桌宠”入口〔中〕

- [ ] 重复启动时唤回已有桌宠；增加托盘的关闭穿透、找回角色、退出入口，并检测快捷键注册失败。
- 证据：`app/main.js:720` 每次启动直接建窗，未使用单实例锁；`:723` 未检查 `Ctrl+Alt+Y` 注册是否成功。
- 影响：多个进程有各自的语音协调器，却共享用户状态；快捷键冲突时，鼠标穿透缺少可靠后备恢复入口。
- 状态：源码确认保护缺失，本轮没有实际启动第二份程序。
- 验收：连续启动多次始终只保留一只角色；快捷键被占用时仍可恢复操作。

### B04 · P2 · 菜单适应小屏幕和高系统缩放〔小至中〕

- [ ] 菜单高度随工作区收缩，正文滚动，标题／拖动区始终可达；显示器变化时重新校准位置。
- 证据：`app/main.js:400`、`:424`、`:435`。固定高度为 636，边界函数假定屏幕足够高。
- 已模拟：逻辑工作区为 900×540 时，菜单 y 被算成 −104，标题可移出屏幕；普通 1920×1080 工作区对照正常。这里的尺寸为逻辑像素，不是面板物理分辨率。
- 验收：小屏幕及 100%／125%／150%／200% 缩放下能看到关闭和拖动区域；拔掉外接屏后可以找回菜单。

### B05 · P2 · 天气缓存绑定地点，阻止旧请求覆盖新城市〔中〕

- [ ] 缓存保存地点标识；切换地点时持久化失效旧缓存；请求完成时检查地点和请求版本。
- 证据：`app/weather-service.js:237`、`:287`、`:303`、`:363`。
- 已模拟 A：切换到上海市黄浦区后断网，重建服务显示新城市名称，却读取旧城市的 33℃缓存。
- 已模拟 B：新城市先返回 11℃，更早发出的旧城市请求后返回 35℃，结果新城市界面被覆盖为 35℃。
- 验收：快速切城、断网切城后重启、请求乱序返回，均不混用地区数据。

### B06 · P2 · 天气停用／切城后让排队提醒立即失效〔小至中〕

- [ ] 停用和切城时清理对应队列；派发前重验当前地点、开关和数据时效，重新构造天气字幕。
- 证据：`app/main.js:798`；`app/trigger-engine.js:241`、`:407`。
- 已模拟：雷雨提醒在说话期间入队，随后停用天气；待播放槽释放后仍播出旧雷雨提醒。
- 验收：停用后不再派发此前尚未开始的天气提醒；切城后不播旧地点信息。

### B07 · P2 · 安静时间不能堵住允许的点击回应〔小至中〕

- [ ] 从队列中选择“当前允许派发”的最高优先级事件，而不是只检查第一项。
- 证据：`app/trigger-engine.js:411`、`:420`。
- 已模拟：00:59 排队雷雨 → 01:00 进入安静时间 → 用户点击。天气在队首被禁止，但后面的点击也一直无法派发。
- 验收：主动提醒保持安静，用户主动互动仍依约响应；禁止事件不会阻塞其他允许事件。

### B08 · P2 · “仅恶劣天气”正确处理多个同时存在的条件〔中〕

- [ ] 先收集降雨、温度、大风等条件，再按提醒模式与优先级筛选、合并。
- 证据：`app/trigger-engine.js:219`、`:252`、`:336`。
- 已模拟：小雨伴 34℃、体感 36℃及大风，先选了普通下雨，再被“仅恶劣”模式过滤，高温／大风未获得后续判断。
- 补充：晴天转大风的“重要变化”判断没有纳入 `windy`，需一并补齐。
- 验收：复合条件选出当前模式允许的信息，避免漏掉条件或连续说多条。

### B09 · P2 · 天气刷新失败不要显示成功〔小〕

- 验收：失败明确显示“获取失败，正在使用某时缓存”；保留已有可用数据，成功后恢复正常状态。

### B10 · P2 · 说话结束后保留用户刚选的表情〔小至中〕

- 验收：手动选择优先；点击临时表情仍能按期限恢复；连续语音不会丢失恢复目标。

### B11 · P2 · 设置保存防抖、原子替换与损坏回退〔中〕

## 策略选择与可选优化

以下属于需要决定的交互规则或新功能，不都属于 bug。

### C01 · 优先推荐 · 点击回应更及时〔中〕

- [ ] 将点击回应与主动提醒的冷却、数量统计、有效期分开。
- 现状已模拟：普通档在上一句结束后点击，仍受 90 秒全局冷却；一次测试里，点击发生 81 秒后才出现连击吐槽。点击还会增加主动发言计数。三档全局冷却分别为 180／90／60 秒。
- 推荐方向：点击可以有独立短冷却；若忙碌且短时间内不能回应，就只保留表情反馈，及时丢弃过时点击事件；不占用主动提醒每日额度。具体冷却和有效期由你决定。
- “第三次点击即时识别”目前不等于“语音即时播放”。

### C02 · 优先推荐 · 随时可控的声音和字幕〔中〕

- [ ] 总音量、静音、停止当前语音、字幕开关，以及“安静 30／60 分钟”。
- 需确定：静音后是否仍允许文字字幕。主动提醒总开关、声音开关和字幕开关应各自有明确含义。
- 延续当前预生成语音方案，不要求接入语言模型或动态合成。

### C03 · 推荐 · 让用户知道“为什么这次没说话”〔小至中〕

- [ ] 增加简明状态：正在说话、冷却中、安静时间、今日主动次数、天气缓存年龄；提供可选诊断记录。
- 收益：把概率未命中、策略抑制、播放失败区分开，方便以后判断是真 bug 还是既定规则，也便于提供复现信息。

### C04 · 可选 · 专注／全屏场景控制〔中〕

- [ ] 提供手动专注模式，再考虑全屏或演示时暂停主动说话、缩小或暂时隐藏角色。
- 需确定：退出专注后直接恢复，还是丢弃期间积压的提醒。推荐丢弃过时闲聊，仅保留仍有意义的事项。

### C05 · 可选 · 低功耗与不同刷新率一致性〔中〕

- [ ] 先量测空闲／拖动／说话时 CPU、GPU、帧耗时，再决定节流幅度。
- 代码事实：`renderer.js:126`、`:481` 每约 180ms 提取舞台像素用于命中检测；`:287` 的口型平滑系数按帧固定。
- 可做：鼠标远离时减少像素读取，降低空闲采样；口型改为按时间平滑并增加阈值迟滞，让 30／60／144Hz 表现接近。
- 未实测低配机器，不能据此断定它就是之前音频听感卡顿的原因。

### C06 · 后续 · 分发与跨电脑验收〔中至大〕

- [ ] 增加设置导出／导入、正式安装与卸载、图标、版本信息、构建后自动核对资源。
- [ ] 执行 6–12 小时运行，覆盖休眠解锁、音频设备切换、断网重连、混合 DPI 双屏、拔屏、重启保留设置；补口型和队列回归入口。
- [ ] 公开发行前完成项目既有的第三方许可与素材授权确认事项。

## 建议选择顺序

1. **第一轮：B01 + B02 + B10。** 修口型可见性、播放异常恢复和表情归属；直接覆盖此前最影响体验的区域。
2. **第二轮：B03 + B04 + B11 + B12。** 解决找不回角色、菜单越界、设置可靠性和拖动细节。
3. **第三轮：B05–B09 + C01。** 使天气与主动行为既准确又及时。
4. **第四轮：从 C02–C06 中选择。** 优先建议音量／静音／停止播放，其次诊断状态，再决定专注和发行能力。

所有复选框都表示待决定或待实现，不表示已经修复。可直接按编号指定下一轮范围，例如“先做 B01、B02、B10，再做 C02”。
